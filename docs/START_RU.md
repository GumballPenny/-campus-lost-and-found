# Запуск и показ проекта

Все команды выполняются **в папке campus-lost-and-found**. В IntelliJ откройте
нижнюю вкладку Terminal. Нужны Java 21 и установленный PostgreSQL 18.
Скрипты сами находят Maven из установленной IntelliJ, поэтому установка `mvn`
в PATH не обязательна.

## 1. Финальный проект без настройки Docker на ноутбуке

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-local-final.ps1
```

Дождитесь сборки и запуска (первый раз дольше из-за скачивания зависимостей).
Откройте **http://localhost:8080/**. Если страница ещё не открывается, подождите
несколько секунд и обновите. Ошибки смотрите в `.local/logs/items.log` и
`.local/logs/accounts.log`.

Скрипт запускает **две отдельные Java-программы** и собственный PostgreSQL:
items :8080, accounts :18081, PostgreSQL :55440. Существующая база `css` на
:5432 не используется. В локальном режиме две базы живут в одном сервере
PostgreSQL; в Docker для них предусмотрены два отдельных контейнера.

Создаются базы и таблицы, а **пользователей создаёт ваша регистрация**.
Данные лежат в `.local/demo-postgres` и сохраняются после остановки.
Не удаляйте `.env`: там ключ и пароль именно этой демонстрационной базы.
`.env` и `.local` исключены из Git.

Остановка: **Ctrl+C в том же терминале**. Скрипт останавливает свои процессы.
Для повторного запуска выполните ту же команду. Не запускайте его одновременно
с другим запуском проекта на 8080. Если порт занят, остановите прошлый Run в IDE.

## 2. Демонстрация финального проекта за 3–4 минуты

1. На странице нажмите **Регистрация**. Придумайте логин латиницей, имя и пароль
   от 8 символов. Приглашение оставьте пустым. Нажмите **Создать аккаунт**.
2. Покажите имя и **ROLE_FINDER**. Это данные `/api/me`, роль назначил сервер.
3. В новой записи введите уникальный ключ, например `LF-DEMO-01`, и «Рюкзак».
   Нажмите **Зарегистрировать**: **201**, статус **REPORTED**, появился UUID.
4. Нажмите **Найдено · CUSTODIAN**: **403 FORBIDDEN**, статус остался REPORTED.
5. Нажмите **Выйти**. В `.env` локально посмотрите `CSS_CUSTODIAN_INVITE`.
   Зарегистрируйте второй аккаунт с этим приглашением: **ROLE_CUSTODIAN**.
   Этот код не надо показывать аудитории или выкладывать на GitHub.
6. Нажмите **Обновить**, найдите рюкзак, нажмите **Найдено**:
   **200**, статус **FOUND**. Повторный такой переход даст **409**.
7. Нажмите **Проверить вызов без токена**: **401**, виден `correlationId`.
8. Выйдите, снова войдите в первый аккаунт. Вещь остаётся в списке.
   Можно остановить/запустить скрипт и войти снова: аккаунт и вещь сохранятся.

Это реальные HTTP-запросы и PostgreSQL, а не нарисованные ответы.

## 3. Чистая демонстрация Lab 5

Откройте ветку **lab5-security** в том же репозитории. Нужна ваша существующая
локальная база `css`, к которой у пользователя есть права на таблицы и миграции.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-dev.ps1
```

Введите имя пользователя и пароль **PostgreSQL**, когда скрипт попросит.
Это не пароль от страницы. Если ваша база называется иначе, перед запуском:

```powershell
$env:DB_URL='jdbc:postgresql://localhost:5432/ИМЯ_БАЗЫ'
```

Откройте **http://localhost:8080/**. В dev входите как `finder`, затем
`custodian`, у обоих пароль `campus-dev`. Покажите создание 201, junior 403,
senior FOUND и после выхода 401. Пользователи хранятся в памяти, таблицы users
в этой версии нет. Это соответствует отдельному заданию Lab 5.

В IntelliJ можно открыть `config/Application.java`, нажать зелёный треугольник
рядом с `main`, предварительно указав DB_URL/DB_USERNAME/DB_PASSWORD в Environment
variables этой Run Configuration. Для новичка скрипт проще: он спросит пароль.

## 4. Проверка тестами без удаления ваших демонстрационных вещей

```powershell
powershell -ExecutionPolicy Bypass -File scripts/verify-isolated.ps1
```

Скрипт поднимает отдельный тестовый PostgreSQL, запускает `verify` у имеющихся
сервисов и останавливает базу. Ожидайте строку **PASS**. При `-q` Maven не обязан
печатать BUILD SUCCESS: важны отсутствие ошибок и успешный код завершения.
Отчёты: `target/surefire-reports`, у accounts — свой `target/surefire-reports`.

Не направляйте интеграционные тесты в рабочую базу: они выполняют DELETE
тестируемых строк. Изолированный скрипт не использует существующую базу css.

## 5. Финальный вариант в Docker

Требуется работающий Docker Engine, не только установленная иконка Docker Desktop.
Проверьте `docker info`: должна быть секция Server без ошибки соединения.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup-env.ps1
docker compose up -d --build
docker compose ps
```

`setup-env.ps1` выполняют **один раз**. Если `.env` уже создал локальный скрипт,
пропустите этот шаг. Откройте http://localhost:8080/. Регистрация и показ — как
в пункте 2. Данные Docker лежат в его томах и независимы от локальной демонстрации.

Логи: `docker compose logs --tail=100 items accounts`.
Остановка: `docker compose down`. Не добавляйте `-v`, если хотите оставить данные.

## 6. GitHub и PR

Ветки Lab 5 и final подготовлены отдельно. Перед публикацией проверьте:

```powershell
git status
git log -2 --oneline
git push -u origin lab5-security
git push -u origin final-microservices
```

На GitHub откройте **Pull requests → New pull request**.
Для Lab 5 выберите base `lab-3-tests-sql-jdbc`, compare `lab5-security`, заголовок
**CSS-67 Add Campus JWT security and auth page**.
Эта база исключает из PR изменения Lab 3. Lab 4 ещё не была опубликована,
поэтому её REST-часть входит в проверяемый diff. Чеклист лежит в `docs/PR_LAB5.md`.

Для final compare — `final-microservices`, заголовок
**CSS-67 Add account microservice and deployment**; checklist — `docs/PR_FINAL.md`.
Чтобы final PR показывал только добавления final, его base — `lab5-security`;
после слияния Lab 5 переключите base на main.

Новый push в ту же ветку автоматически обновляет открытый PR. Создавать новый
PR при каждой правке не нужно. Слияние выполняйте после проверки/сдачи.
